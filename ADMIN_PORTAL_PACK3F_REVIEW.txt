================================================================================
2. CANONICAL REPOSITORY LAYER INTEGRATION
================================================================================
All platform data and governance actions are executed via authoritative repositories:
- Application Onboarding & Review:
  - Loaded via `ApplicationRepository.listAll()`
  - Approved via `ApplicationRepository.updateStatus(appId, 'APPROVED', activeUser.id)`
  - Rejected via `ApplicationRepository.updateStatus(appId, 'REJECTED', activeUser.id, reason)`
  - Revisions requested via `ApplicationRepository.updateStatus(appId, 'PENDING', activeUser.id, note)`
- Restaurant Governance:
  - Suspended via `RestaurantRepository.suspendRestaurant(restaurantId, reason)` (calls PostgreSQL RPC `suspend_restaurant`)
  - Reactivated via `RestaurantRepository.reactivateRestaurant(restaurantId)` (calls PostgreSQL RPC `reactivate_restaurant`)
  - Verified via `RestaurantRepository.update(restaurantId, { tinNumber, businessLicenseNumber, isVerified: true, verificationStatus: 'VERIFIED', sellerTier: 'VERIFIED_SELLER' })`
- Catalog & Quality Reports:
  - Resolved via `DataReportsRepository.resolveReport(reportId, activeUser.id, status, notes)`
- Platform Identity & Role Management:
  - Loaded via `ProfileAdminRepository.listAll()`
  - Roles granted/revoked via `ProfileAdminRepository.changeRole(userId, newRole, newAccountType)` (calls PostgreSQL RPC `change_platform_role`)
  - Self-revocation prevention enforced at frontend and database RPC level.
- Orders:
  - Loaded via `OrderRepository.listAll()`
- Payments:
  - Loaded via `PaymentRepository.listAll()`
- Audit Logs:
  - Loaded via `AuditLogRepository.listAll()`
  - Logged via `AuditLogRepository.logAction()`

================================================================================
3. FINANCIAL KPI INTEGRITY & HONESTY
================================================================================
- Gross volume (TZS) is computed strictly from real `public.payments` where `status === 'SUCCESS'`.
- Non-successful payments (`PENDING`, `FAILED`, `CANCELLED`, `REFUNDED`) are strictly excluded from gross volume.
- Platform revenue (TZS) is calculated strictly from persisted `platformCommissionTzs` on successful payments.
- Order volume is derived strictly from real `public.orders`. Completed order counts do not synthesize financial settlement.
- Freshness score does not fabricate 100% when no restaurants exist; returns 0% honestly.
- SystemHealth measures real Supabase configuration and runtime status rather than static "100% Operational" assertions.
